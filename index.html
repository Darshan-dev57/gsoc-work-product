Goals

I spent the program making the checker handle the Java people actually write, then fixing whatever that work exposed. Over the summer I opened 19 pull requests across three repositories: JPF-Core (12), JPF-NAS (5), and jpf-nhandler (2). All 19 are merged.

Abstract

Java Pathfinder finds bugs by running a program down every path it can take. But it was built for older Java. Modern code broke that promise. Sealed classes and records crashed the checker or silently gave wrong answers. The hidden setup calls the compiler generates did the same. My project brings the checker up to modern Java. I completed sealed-class and record support in the core engine. I fixed the text-building and switch machinery around them. I repaired the networking and delegation extensions that work touched. Every fix ships with a test that fails before and passes after, so future contributors build on verified ground.

Feature areas

  • Sealed classes. Read the permitted-subclass list correctly and reject classes that break the seal.
  • Records. Understand record data and run the equality, printing, and hashing code the compiler generates.
  • Pattern-matching switch. Run the type and enum switches Java 17 added.
  • String concatenation. Handle the constants and boxed values modern text building emits.
  • JDK models. Fill the startup hooks and file models Java needs before checking starts.
  • Test infrastructure. Isolation between tests and control over when a run counts as finished.

Technical highlights

Records implementation

  • Component metadata parsed from classfiles with generic signatures and annotations preserved
  • Array components compare by reference identity per JEP 395; boxed JDK types compare by wrapped value through a safe whitelist
  • toString renders actual content instead of heap addresses; hashCode covers nested and multidimensional arrays
  • Reflection support through modeled record components with accessor and annotation queries

Bootstrap methods

  • StringConcatFactory recipe decoding with resolved static arguments and zero-arg guards
  • SwitchBootstraps dispatch for type switches (instanceof matching) and enum switches, with null fall-through per host convention
  • ASM-generated tests checked against host JDK 17 behavior first

Sealed classes support

  • Permitted-subclass metadata parsed into class info and covered by direct classfile tests
  • Parsing tests confirm the pre-fix failures before the shadowing fix lands
  • Consistent name handling between storage and comparison paths

  • Small pull requests. Combined work was split per reviewer feedback, so each change is independently reviewable and revertible.

  • Programs that load. Clojure reaches its test code instead of dying in jar loading. The KnockKnock socket dialogue completes end to end. Jar delegation runs past entry lookup.
  • Suites that prove it. Serialization 9 of 9, sockets 5 of 5 with zero orphan warnings, delegation 35 of 35, core suites 1028, 1066, and 1071 green.

Challenges & Solutions

What was difficult and how it was solved.

The hardest part was not implementing individual features. It was learning a large, unfamiliar codebase. I had to determine where Java 17 behavior was handled, what already worked, what silently failed, and where the actual compatibility gaps were.

Understanding an unfamiliar codebase. JPF spans a model-checking VM, bytecode execution, JDK models, native peers, and several extension repositories. Before changing code, I had to trace how a Java feature moved through these layers and identify the correct implementation point. I gradually built a mental model of the execution path. I read existing implementations, followed call chains, and compared related features. I used small experiments to validate my assumptions.
Finding what actually worked, and what did not. Java 17 support was rarely a simple "implemented / not implemented" problem. Some features appeared to work but produced incorrect behavior in specific cases, while others failed much later in execution. I used small, focused Java programs and regression tests to isolate behavior. I compared JPF's execution with the host JVM. That comparison showed whether a failure came from parsing, bytecode execution, a bootstrap method, a JDK model, or the surrounding infrastructure.
Tracing failures across abstraction layers. A visible failure was often several layers removed from its actual cause. A Java language feature can compile correctly, reach JPF successfully, and only fail when a bootstrap method, reflection path, or modeled JDK class runs. I traced execution from the Java source through class-file behavior into JPF's VM. Then I traced it back into the relevant model or peer implementation.
Bridging host-JVM behavior with JPF's modeled execution. One of the hardest problems was that JPF does not simply execute Java using the host JVM. It models parts of the JVM and JDK itself, which means Java 17 behavior had to be reproduced inside JPF's execution model. A feature can behave correctly on the real JVM but still fail in JPF. The cause is a missing or different bytecode handler, bootstrap method, JDK model, or native peer. I treated the host JVM as the behavioral reference. I built minimal programs to isolate the difference. I traced the execution through JPF's VM and models. Then I implemented and regression-tested the missing behavior.
Working with incomplete compatibility assumptions. A major challenge was discovering that existing JPF implementations often encoded assumptions from older Java versions. Supporting Java 17 meant identifying which assumptions were still valid and which had become incorrect as the JDK and class-file behavior evolved. I did not replace working code wholesale. I compared the existing implementation with actual Java 17 behavior. I extended it only where the underlying assumption no longer held.
Reproducing JVM behavior outside the JPF environment. Some failures were difficult to understand from JPF's code alone because the expected behavior was defined by the real JVM and JDK. I used small standalone Java programs to observe host-JVM behavior first, then used those observations as a reference while implementing the corresponding JPF behavior. This was particularly useful for invokedynamic, bootstrap methods, string concatenation, records, and newer JDK APIs.
Validating changes without breaking existing behavior. JPF is a model checker, so a change that makes one Java 17 example pass is not enough. Every fix had to be checked against existing behavior and regression tests. I repeatedly moved between a minimal reproducer, the implementation, and the broader test suite to make sure a local fix did not introduce regressions elsewhere.
Large combined changes. My networking work initially arrived as one large pull request. Review feedback showed that the change was easier to understand and validate when separated. I split it into focused changes covering build updates, formatting, cleanup, and peer fixes. Each piece was easier to review and merge independently.
  1. Understand existing behavior
  2. Find a minimal reproducer
  3. Compare with the real JVM
  4. Trace JPF's execution path
  5. Identify the compatibility gap
  6. Implement the smallest fix
  7. Add a regression test
  8. Run the broader test suite
  9. Repeat

The biggest lesson was that supporting a new Java version in a mature JVM-based system is less about adding isolated features and more about understanding how those features interact with the existing execution model.

Remaining Work

The implementation is in place; the remaining work is focused on integration, release updates, and long-term maintenance.

  • Merge Java 17 support into the main development line. Complete the remaining review and integration work, then transition the java-17 branch into the project's main/master development branch once the maintainers are ready.
  • Keep JPF aligned with new Java releases. Continue updating the project as newer Java/JDK releases introduce changes to class-file formats, JVM behavior, language features, APIs, and runtime internals.
  • Refine and maintain the codebases. Continue cleaning up implementations. Improve consistency across JPF-Core and its related repositories. Address reviewer feedback. Maintain the new Java 17 support as the surrounding code evolves.
  • Continue regression testing and compatibility validation. Keep expanding and maintaining tests around Java 17 behavior and verify that future changes do not regress the functionality already implemented.
